1.0 SCOPE 
The scope of this protocol covers the Protocol Version defined in the footer of this document. 
Note: The protocol version was not upgraded between BMS v11 and v13 when the AUX IO 
feature was added, however, the protocol remained backward compatible. 
This document specifies the CAN communication between the Altairnano Battery 
Management System (BMS) and an application to which it is to be connected.  The interface is 
general purpose, with options for a given application. 
The BMS electronics consist of two types of electronic units: the BMU (battery management 
unit) and the LMU (local monitoring unit).  An ACU (application control unit) interfaces to the 
BMU over an “external” CAN bus, while the BMU communicates to the LMU(s) over an 
“internal”” CAN bus. 
Altairnano also provides “BMS Service Tool” software for a personal computer which can be 
used to communicate with the BMS for diagnostics, service, and reprogramming.  A PC-to-
CAN adapter enables the PC to connect to the CAN bus; the PC-to-CAN adapter typically 
connects to the PC over USB.

3.3 
BMU OPERATING STATES 
The BMU utilizes a finite state machine to coordinate its operating state with the ACU. The 
application’s desired BMU “steady state” is always IDLE, READY, or POWER-DOWN-
READY.  The other states are “transient”, meaning the BMU only stays in those states 
temporarily while transitioning to a steady state.

3.4 
“DISCONNECT TOO SLOW” E-STOP DTC 
If the BMU is in the STOPPING state for longer than a timeout period (approximately 5 
seconds), the BMU shall activate a Level 4 (E-STOP) DTC (“Disconnect too slow”). 
 
3.5 
SLEEP MODE 
The “Sleep Mode” is an ultra-low-power mode in which the BMU’s power supply is on but the 
BMS does not perform any calculations or send any CAN messages, and in which all outputs 
are put into their passive (unpowered) state.  It essentially means the BMU and LMUs have 
powered themselves off under software control. 
The BMU enters “Sleep Mode” within 10 seconds in POWER-DOWN-READY state.

4.0 HANDSHAKING SEQUENCES 
4.1 
POWER UP AND POWER DOWN 
If the “BMU On/Off” input transitions from low to high while the BMU is in “sleep mode”, then 
the BMU shall exit “sleep mode” and enter POWER-UP state. 
If the BMU power supply and the “BMU On/Off” input transitions from low to high at the same 
time, the BMU shall enter the POWER-UP state. 
[If configured to sleep when “BMU On/Off” is OFF] When the BMU is powered and the “BMU 
On/Off” input is in the low state, the BMU shall act as though the “BMU Desired State” is 
POWER-DOWN-READY, regardless of the value in the Application Command Message. 
When the BMU is powered and the “BMU On/Off” input is in the high state, the BMU shall 
follow the “BMU Desired State” from the Application Command Message per state transition 
logic specified in this document.

5.0 CAN COMMUNICATION 
5.1 
GENERAL 
The following describes general information utilized when working with the communication 
protocol. 
5.1.1 
SCALING OF VARIABLES 
(a) Cell-Group Voltages are unsigned, 16-bit, MSB-first, with a resolution of 1/8192 V 
(122 V) per bit.  The valid range of values is 0 – 4v.  See Section Data Error Codes 
error response codes. 
(b) Temperatures are signed, 16-bit, MSB-first, with a resolution of 1/64 deg C (0.015625 
deg C) per bit.  The valid range of values is -200 to +200 C. See Section Data Error 
Codes error response codes. 
(c) Pack voltages are signed, 16-bit, MSB-first, with a resolution of 1/16 V (62.5 mV) per 
bit.  The valid range of values is 0 – 2047v.  See Section Data Error Codes error 
response codes. 
(d) Current values are signed, 16-bit, MSB-first, with a resolution of 1/8 Amp (0.125 A) 
per bit.  The valid range is -4000 Amps to +4000 Amps.  Positive is charging; negative 
is discharging.  See Section Data Error Codes error response codes. 
(e) SOC values are unsigned, 8-bit, with a resolution of 0.5% per bit.  A value of 0xFF is 
used to indicate the value is “Unknown”. 
5.1.2 
DATA ERROR CODES 
The following data error codes indicate that a value is unknown for a particular reason. For 
variables that contain negative values remember that those values will have the highest bit 
set. Therefore, a value of 0x8000 and greater can be valid.

5.1.3 
CAN IDS 
(a) CAN-IDs shall use J1939 format (29-bit identifiers), using “Proprietary B” PGNs, 
except the Application Command Message, which uses the “Proprietary A” PGN. 
(b) Priority of CAN messages shall be 6 (that is, 0b110). 
(c) The reserved and data page bits for CAN messages defined in this specification shall 
be 0. 
(d) The BMU’s pre-selected source address, which is represented by ‘xx’ in the message 
definition section in this document, shall have a factory default value of 0x03. 
(e) The Application’s pre-selected source address, which is represented by ‘yy’ in the 
message definition section of this document, shall have a factory default value of 
0x20. 
(f) All CAN messages in this specification transmitted by the BMU and Application shall 
use 8 data bytes (i.e. data length code = 8), even if some bytes do not carry 
meaningful data.

6.0 MULTI-STRING COORDINATION 
The BMS supports coordination of multiple battery strings connected in parallel.  When 
operated this way, each string has its own BMU and set of LMUs; one of the strings BMU acts 
as a “Multi-String Coordinator”.  The “Multi-String Coordinator” sends commands to the BMU 
of all other strings and receives information from them. 
The Application Control Unit (ACU) communicates with the Multi-String Coordinator using 
CAN messages defined in this section. 
Any of the string BMUs can act as the coordinator; all are configured identically, except for 
CAN addresses.  Only one can be coordinator at a time, however.  Whichever BMU receives 
the Multi-String Application Command Message from the Application Control Unit will act as 
the coordinator.

6.1 
SWITCHOVER IN CASE OF MULTI-STRING COORDINATOR FAILURE 
Several additional requirements enable the Application Control Unit to dynamically change 
which of the BMUs is acting as “Multi-String Coordinator”.  The requirements are as follows: 
(a) If the BMU acting as “Multi-String Coordinator” fails, the Application Control Unit can 
switch the destination address of its “Multi-string Application Command” messages to 
one of the other strings BMU. 
(b) A string’s BMU shall accept “Application Command Messages” from either the pre-
specified Application Control Unit’s address, or from the address of any of the other 
BMUs (which would send the message only when acting as “Multi-String 
Coordinator”). 
(c) If a string’s BMU is receiving “Application Command Messages” from a given 
“application address”, it shall ignore “Application Command Messages” from all other 
addresses until the message from the current “application address” times out.  After 
that, the string’s BMU can receive “Application Command Message” from any of the 
allowed addresses.

Data3.) 
The String Bit Map enables the Application Control Unit to take one or more strings 
offline if required.  For example, if a string has a failure that causes it to go offline, it 
may be necessary to rebalance the strings after the DTC condition is eliminated.  In 
that case, the Application Control Unit could operate the pack with a ‘0’ for the 
previously failed string until the point where connecting the string is appropriate, as by 
the Section 6.2, Connect Voltage Flags. 
(e) Aux Command Bit Map – is the Aux IO Output Control 
• 
Bit 0 = String 1, Bit 1 = String 2, etc… If set to ‘1’, the Aux Output is active. 
(f) Transmit Period: See Application Command Message in Section 5.2.12 
• 
If a BMU does not receive the Multi-string Application Command Message for 
the defined period, then the BMU will stop executing as “Multi-string 
Coordinator”.
